# Promhis Roadmap — going from internal tool to a real product

This is the working plan for turning Promhis into something publishable: open source on GitHub, self-hostable, documented, and sold as a licensed Enterprise edition of the same self-hosted image. Written down before execution per request, so scope is explicit and checkable rather than discovered mid-build.

**Business-model pivot (2026-11-06):** earlier passes of this document planned a hosted/cloud offering on AWS (§3) alongside tiered cloud pricing (§9). That's cancelled — no managed/cloud offering, no AWS. The model is now open-core: publish on GitHub, Community edition free forever, Enterprise edition is the same image unlocked by a signed license file (§15). §3 and the original §9 pricing table are kept below for history but are no longer current — see §15 onward and `PRICING.md` for what actually shipped.

**Licensing pivot (2026-11-10):** the open-core/licensing model built in §15/§19/§22/§23 (and the `rbac`-gated admin cap in §21) is reverted. This project stays fully FOSS (MIT) for now — every feature that was licensed (multiple admin users, custom branding, incident notes, more than one API token) is free and uncapped. `src/promhis/licensing.py`, `src/promhis/ee/`, `PRICING.md`, and `docs/licensing.md` were removed. A licensing/paid-tier model may be reintroduced later based on real user interest, not preemptively. §15/§19/§21–§24 are kept below for history only.

## Design principle: extensible by construction

Explicit requirement: new integrations (notification channels today; conceivably other things later — e.g. alternate ingest sources, auth schemes) must be addable without touching core dispatch logic. Concretely:

- **Notification channels (§6):** a single `NotificationChannel` interface (`async def send(self, event: AlertEvent) -> None`) that every integration implements, one module per channel under `src/promhis/notifications/`, and a registry mapping config keys to instances. The ingest path loops over *configured* channels generically — no `if slack: ... elif discord: ...` branching. Adding integration #7 later means one new file + one registry entry.
- **Ingest authentication (§5):** likewise built as a small `WebhookAuthenticator` interface rather than hardcoding one scheme, so Basic and Bearer (and anything added later) are two implementations of the same interface, not a growing if/elif in `auth.py`.
- Each integration's failure is isolated from the others and from the core request/response path — a bad/slow channel never blocks ingest or another channel.

This is the pattern to default to elsewhere too: prefer a small interface + registry over branching logic whenever "more of these will probably show up later" is true (already true for `PROMHIS_NODE_LABELS`-style extraction, now also for notification channels and auth schemes) — but don't manufacture abstraction for things with no concrete second case yet.

## Explicit non-goals (for now)

These were raised and deliberately deferred — not forgotten, just not in this pass:

- **No real billing/metering enforcement.** Enterprise licensing (§15) gates *features*, not usage — there is no usage metering, no per-seat/per-volume billing, no Stripe integration, no self-service purchase flow. Issuing a license is a manual, out-of-band process (`promhis-license issue`, run by whoever owns the signing key). Building real metering/billing is a separate, materially larger project, not bolted on opportunistically.
- **No multi-tenancy.** Every deployment is single-tenant under the hood, self-hosted by whoever runs it — there is no hosted/cloud offering (see the pivot note above) and no shared control-plane server. §21's user-management system adds multiple *admin users* to one instance, which is not multi-tenancy — it's still one organization's one instance, one database.
- **No GitHub publish yet.** Everything below is prepared locally. Pushing to a public repo (and picking its name/visibility) happens only after explicit go-ahead with a target repo.

- [x] Found and fixed a real bug during that verification: the async engine used SQLAlchemy's default pooling, which reuses a connection across requests — asyncpg connections are bound to the event loop that created them, so a connection handed out in a different loop raises `RuntimeError`/`InterfaceError`. ## 5. Ingest authentication + audit log — done

Two related asks: (a) the webhook endpoint must not blindly accept alerts — it needs an auth mechanism Alertmanager's own config can set; (b) every ingest attempt should leave a durable, browsable record (source IP, auth outcome, etc.) for debugging *and* basic security visibility ("who's actually sending alerts here").

- [x] `src/promhis/auth.py`: `WebhookAuthenticator` `Protocol` with two implementations, `BasicAuthenticator` (existing behavior, now reading the `Authorization` header directly instead of via FastAPI's `HTTPBasic` security dependency, so it has the same shape as `BearerAuthenticator`) and `BearerAuthenticator` (checks `Authorization: Bearer <token>` against `PROMHIS_WEBHOOK_TOKEN`). Selected via `PROMHIS_WEBHOOK_AUTH_MODE=basic|bearer`, default `basic`.
- [x] Every ingest request — accepted *or* rejected — gets an audit entry. The webhook route checks auth and parses the body explicitly now (not via a short-circuiting `Depends`), specifically so every branch (missing creds, bad creds, malformed payload, success) can be logged before responding.
- [x] `AuditLogEntry` table: timestamp, source IP (`request.client.host`, correct automatically once `PROMHIS_TRUST_PROXY` is honored via uvicorn's `proxy_headers` — see §3), user agent, auth mode attempted, auth result (`success`/`failure`/`missing`), HTTP status returned, alert count (when parseable), receiver name, error detail for rejections/parse failures.
- [x] Dashboard page, `/audit-log` (4th nav tab) — paginated, filterable by outcome, reusing the existing `.register` table and `.flap` status-label components.
- [x] `GET /api/v1/audit-log` (session-authenticated), backing that page.
- [x] Pruned on the same retention schedule as alert events (wired into the existing retention loop in `main.py`).
- [x] Tests (`tests/test_webhook.py`, `tests/test_audit.py`): missing/bad/valid credentials, malformed payload, bearer-mode auth, every outcome recorded correctly, outcome filtering, audit API requires login. Verified against both SQLite and a real Postgres container (14/14 passing both).
- [x] Found and fixed a real pre-existing test-isolation bug while adding these: the whole test suite shared one SQLite file with no cleanup between tests, so a row inserted by one test file could silently change another file's count assertions. Fixed with an autouse-adjacent truncate in the `client` fixture (`tests/conftest.py`) rather than dodging it with yet another unique fingerprint.
- [x] Manually verified end-to-end in a running container too (not just pytest): both auth modes, all four audit outcomes, real source IP recorded correctly.

## 6. Outbound notification forwarding (real feature, not pricing-page vaporware) — done, config path superseded by §13

The channel implementations and dispatch logic below are done and stay as built. **How channels get configured changes** — see §13: env vars are being replaced with a web UI, per explicit follow-up instruction ("no env stuff"). Don't re-read the env-var config bullets below as the current story for *configuring* a channel; they're accurate for how dispatch/error-isolation/the registry *pattern* works, which §13 builds on rather than replaces.

Promhis currently only *receives* from Alertmanager. This adds the other direction, built per the extensibility principle above — not as one-off hardcoded integrations.

- [x] `src/promhis/notifications/base.py` — `NotificationChannel` `Protocol` plus the shared `post_json` helper (one `httpx.AsyncClient`, catches `httpx.HTTPError`, logs and swallows — never raises) and small shared helpers (`severity_color`, `alert_link`, `summary_line`) every channel uses.
- [x] `src/promhis/notifications/{slack,discord,teams,pagerduty,opsgenie,webhook}.py` — one class per channel. Slack/Discord/Teams are simple one-shot notifications; PagerDuty and Opsgenie are state-aware (`trigger`/`resolve` keyed by fingerprint as PagerDuty's `dedup_key`; create/close keyed by fingerprint as Opsgenie's `alias`) so a resolution in Alertmanager auto-resolves the downstream incident too. `webhook.py` is the generic custom-webhook case: posts the raw alert event JSON, no service-specific formatting.
- [x] `src/promhis/notifications/registry.py` — `build_registry()` maps a config key to its channel instance, built fresh from current settings each call (not cached at import — this is what makes it monkeypatch-friendly in tests, and correct if config ever needs to be re-read). A channel with no config present is simply absent from the dict.
- [x] Dispatch wired into `routers/webhook.py`: after persisting and audit-logging, fans out to every channel in the registry via `asyncio.gather(..., return_exceptions=True)` — adding channel #7 means one new module + one registry line, this loop never changes.
- [x] Error isolation at two layers: `post_json` itself never raises, and `return_exceptions=True` on the gather is a second guarantee. Verified both in unit tests and a real end-to-end container test (a channel whose `send()` raises `RuntimeError` still leaves the webhook returning 200).
- [x] Config via env vars (`PROMHIS_SLACK_WEBHOOK_URL`, `PROMHIS_DISCORD_WEBHOOK_URL`, `PROMHIS_TEAMS_WEBHOOK_URL`, `PROMHIS_PAGERDUTY_ROUTING_KEY`, `PROMHIS_OPSGENIE_API_KEY`, `PROMHIS_CUSTOM_WEBHOOK_URL`), plus `PROMHIS_PUBLIC_BASE_URL` (optional) for "view in Promhis" links in the notifications that support them.
- [x] Tests (`tests/test_notifications.py`, 10 tests): registry inclusion/exclusion, payload shape per channel (including PagerDuty/Opsgenie's state-aware trigger-vs-resolve and create-vs-close URLs), and the ingest-never-breaks guarantee via a deliberately-failing fake channel. 23/23 total suite passing.
- [x] Manually verified end-to-end in running containers: real HTTP POST confirmed received by a throwaway catcher container for the custom-webhook channel, and `PROMHIS_PUBLIC_BASE_URL` link construction.

## 18. Query scaling: Stats "all time" and the alert ledger — done

Open question (2026-11-06): "what happens if we've accumulated a lot of alerts over time, will the UI lag." Investigated before touching code — found two real unbounded queries (everything else, including the Alerts register, Audit Log, and Nodes pages, was already properly paginated/indexed):

- **`/stats?range=all`** — `crud.events_in_range` fetched *every* `AlertEvent` ever ingested into Python with no limit and no date filter, then `insights.py`'s pure functions looped over the full list in Python to bucket it by day/severity/node. ## 21. User management system (admin users)

Requested (2026-11-06): real admin *accounts* (not just one shared env-var login), with an explicit free/licensed split — **Free is hard-capped at one admin user; the `rbac` feature licensed unlocks more** (terminology aligned with §22's reconciliation — originally scoped as "Community/Enterprise," same decision). This is a genuine auth-system change, not an additive feature, so it's scoped carefully and built/verified in small steps rather than in one pass.

Scope decisions:

- **New `User` table**: `id`, `username` (unique), `password_hash`, `created_at`, `last_login_at`, `is_active`. Passwords hashed with stdlib `hashlib.pbkdf2_hmac` (random per-user salt, high iteration count) — no new dependency, and PBKDF2 at sufficient iterations is still an accepted choice; the old `verify_credentials` didn't actually hash anything, it just constant-time-compared the live `PROMHIS_ADMIN_PASSWORD` value, which doesn't extend to multiple stored accounts.
- **Bootstrap admin, not a breaking migration.** `PROMHIS_ADMIN_USER`/`PROMHIS_ADMIN_PASSWORD` keep working exactly as documented today — on startup, that env-var identity is upserted into the `User` table as the bootstrap admin. An existing self-hosted install upgrading to this version logs in exactly the same way it always has, zero config changes required. This bootstrap user counts toward the admin-count cap.
- **The cap is a runtime check, not a feature flag**: creating a *second* admin user will check `has_feature("rbac")` at creation time (same pattern as §22's other gates) — Free stays capped at the one bootstrap admin; a license with `rbac` can create more via a new "Admin Users" management page (not yet built — see below). Revoking a license later won't delete existing extra admins (consistent with §22's "existing configured things go dormant, not deleted" precedent elsewhere) but will block creating further ones.
- **Login flow changes**: `login_submit` checks credentials against the `User` table (bootstrap admin included) instead of `settings.admin_user`/`admin_password` directly. Existing session-cookie mechanics (same shared session, same cookie) are unaffected — this changes *who can log in*, not *how a session works* once logged in. `require_login`/`require_login_api` don't change at all — they only check session-cookie presence, not credentials, so they're unaffected by how the session was populated.
- **Out of scope for this pass**: per-user permissions/roles (every admin account has full access, same as today's single shared login — this is about *how many people can log in*, not a permissions system), self-service password reset/email flows (admin accounts are created by an existing admin, not self-registered), and `sso` (separate, already-tracked licensed feature in §22, not part of this item).

Built:

- [x] `models.py`: `User` table (`id`, `username` unique/indexed, `password_hash`, `is_bootstrap`, `is_active`, `created_at`, `last_login_at`).
- [x] `auth.py`: `hash_password`/`verify_password` (PBKDF2-HMAC-SHA256, 600k iterations, random 16-byte salt per call — `hash_password("x") != hash_password("x")` on two calls, by design).

- [x] **Login-flow cutover**: `routers/dashboard.py`'s `login_submit` now authenticates against the `User` table (`crud.get_user_by_username` + `verify_password`, checking `is_active`) instead of `verify_credentials`'s direct env-var comparison, and calls `crud.record_login` on success. `verify_credentials` itself is untouched and still used by the *webhook's* `BasicAuthenticator` — a deliberately separate, unrelated gate (machine-to-machine ingest auth, not a dashboard admin account), not migrated to the `User` table.

**Noted, not adopted — conflicts with an already-made decision:**

- **Hosted/managed SaaS tier.** The analysis suggested this could be a bigger revenue stream than on-prem Enterprise licenses. This project already considered and explicitly cancelled a hosted offering (see the pivot note at the top of this document). Not silently reintroducing a reversed strategic decision from a pasted analysis — if this is worth revisiting, that's a deliberate call to make explicitly, not a pricing-table edit.
- **Multi-tenancy / MSP-managing-many-customers.** The analysis flagged this as "one of the most valuable things you could sell." §21/§22 already settled on single-tenant-only as an explicit non-goal. `rbac`'s team-scoped views (role-based visibility within one org) is not the same thing as tenant isolation between separate customers, and the latter is out of scope here — recorded as a real, deliberate tension rather than quietly merged in either direction.

**Not adopted — already free, not a gap:** per-event/line-item "alert fatigue, noisy-rule" detection (flapping + top-noisy-alerts already ship free in the Stats page, §8, and stay free per §22's explicit audit) and PDF/email scheduled reports (already covered by the existing `reports` flag).

**Kept as background, not written into the pricing model:** the competitive-landscape read (Karma's metric-query-based "history" vs. this project's durable event log; Grafana/OpenObserve/Datadog requiring you to move alerting into their platform; the Loki-piping DIY path as the real free-tier alternative; target buyer segments — mid-size self-hosted Prometheus shops, regulated industries needing an audit trail, MSPs/platform teams) — useful positioning context for whoever writes sales/marketing copy later, not itself a product decision to record as "done."
